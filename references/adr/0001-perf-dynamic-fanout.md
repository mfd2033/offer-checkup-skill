# ADR-0001 · offer体检 性能优化：压低单次体检时延（页面取工商 + 单批并行）

- **状态**：采纳（Accepted）
- **日期**：2026-09-20
- **决策人**：用户 + agent（grill-with-docs-pro 流程）
- **关联术语**：见 `references/glossary.md`

## 背景（Context）

单次体检工作流为：browser-skill（`bsk`）抓取 → 实体确认 → 调研维度 → 评分出报告。（初版此处并列写过 WebFetch；ADR-0004 已全局禁用 WebFetch，页面抓取仅走 bsk。）

**本次硬目标（用户明确）**：首要且唯一目标 = 压低单次体检的墙钟时延。正确性与覆盖度不降级，但也不为它们额外牺牲时延。

实测（京东 / 超聚变 / 德之润 / 郑州琛署 四条真实链接，bsk 计时 + WebSearch `responseTimeMs`）：

- 抓取：BOSS 经 browser-skill ≈ 2.0s（navigate 1.1s + snapshot 0.5s）；猎聘/智联经 WebFetch ≈ 1.0s。
- 研究（各维 WebSearch）：单次调用 ~1.3–1.7s；并行总时延由**最慢一跳**决定 —— 京东 抖音 5.6s、超聚变 工商门 4.3s、德之润 工商门 2.4s、琛署 工商门 1.7s。
- **原 ADR（工商门串行门 + 两波式 + 早停）反而更慢**：它给研究阶段强加一个串行「工商门」一跳，使总时延 = 工商门 + max(其余)，比改前「7 维一次性并行」高 ~1.5–2s。早停只裁剪报告章节、不跳过已并发的调用，对时延零贡献。
- 关键发现：BOSS 与猎聘职位页**页面内即自带工商信息**（主体 / 企业类型 / 规模 / 成立时间 / 注册资本 / 经营状态），超聚变、京东、德之润三次抓取均印证。故「主体/类型/规模」无需独立串行工商门调用；仅「参保人数」若页面未给才需少量外部查询。

## 决策（Decision）

采用 **「页面取工商 + 单批并行 + 早停仅裁剪报告」**，逻辑内联进 `SKILL.md`：

1. **抓取即取工商**：链接模式抓取职位页后，直接从页面文本解析工商字段（主体 / 企业类型 / 规模 / 成立 / 注册资本 / 经营状态）。BOSS=snapshot 文本，猎聘/智联=WebFetch 正文，均含该区块。
2. **参保人数按需补查（并行进入批次，不串行）**：若页面已给参保人数 → 不再发工商门调用；若页面未给 → 把「参保人数」作为**并行批次中的一个调用**（与其余维度同消息发出），**绝不前置成串行门**。
3. **单批并行调研**：实体确认后，在**同一条消息**中并发发出全部需要的维度（待遇 / 仲裁 / 套路 / 网络口碑 / 抖音 / 高德 + 可能的参保补查），总时延 = max(各调用)。
4. **硬红线早停 = 仅裁剪报告章节**：命中红线（参保=0 / 主体混淆或自然人独资微型壳 / 仲裁投诉爆量）时，报告中**省略**网络口碑 / 抖音 / 高德三段，但调用已在第 3 步并发发出，故早停不再影响墙钟 —— 它服务于正确性与省 token，明确不再是时延杠杆。
5. **不做结果缓存**（沿用原决策，保新鲜度）：复查/批量场景时延不优化，作为已知妥协记录。

> 若未来要把时延再压一档，唯一结构杠杆是**砍掉慢且常空的软维（抖音/高德，京东曾 5.6s）**，属覆盖度权衡，不在本 ADR 默认开启。

## 后果（Consequences）

- **正面**：时延 ≤ 改前并行基线；当工商门原本是最慢调用时**严格更优** ——
  - 超聚变：研究 4.3s → 1.6s（−2.7s，−63%），端到端 6.3s → 3.6s；
  - 德之润：研究 2.4s → 2.0s（−0.4s）；
  - 琛署：研究 1.7s → 1.5s（−0.2s）；
  - 京东：研究 5.6s（抖音瓶颈）持平，除非砍抖音。
- **成本 / 负面**：页面解析需稳健（工商区块位置各站不同，需容错）；去掉串行门后，「工商门限流兜底」概念消失，改为「页面无参保则并行补查一次」；早停对时延零贡献（诚实记录）。
- **未变**：登录墙失败模式、无缓存妥协、正确性/覆盖度不降级。
