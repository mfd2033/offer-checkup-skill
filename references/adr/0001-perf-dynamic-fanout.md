# ADR-0001 · offer体检 性能优化：动态选维 + 两波并发 + 硬红线早停

- **状态**：提议（Proposed）
- **日期**：2026-09-20
- **决策人**：用户 + agent（grill-with-docs-pro 流程）
- **关联术语**：见 `references/glossary.md`

## 背景（Context）

单次体检当前工作流为：browser-skill 抓取 → 实体确认 → **串行**跑 7 维 WebSearch/WebFetch → 评分出报告。

实测（以 `https://www.zhipin.com/job_detail/223862b6340a8b4a0nJ-0ty7FFtW.html` 为例）与代码核对：

- 招聘站有登录墙：`WebFetch` 秒回但返回「请稍候」空页，链接模式必须依赖 browser-skill 登录态或用户贴文本（属失败模式，非时延问题）。
- 7 维若串行，单次约 **2–3 分钟**；若真并行约 **20–40 秒**。
- 无结果缓存，同公司复查 = 全量重跑。

用户目标（经 grill 四轮确认）：

- 不设硬 SLA 上限，但接受「硬红线早停」以省调用；
- 首要杠杆 = 七维并行化；
- 维度集 = 按风险动态选维；
- 不做缓存（保新鲜度）。

## 决策（Decision）

采用 **两波式并发 + 动态选维 + 硬红线早停**，逻辑内联进 `SKILL.md`：

1. **波1 工商门（必跑）**：实体确认后，先发「参保人数 + 主体一致性」查询（企查查 / 天眼查 / 爱企查，1–2 个调用）。
2. **依据门结果动态选维**：
   - 工商门全被限流拿不到 → **回退全 7 维**保覆盖；
   - 门结果正常 → 进入波2。
3. **波2 同消息全发**：把「门结果判定需要」的其余维度在**同一条消息**中并发发出。
4. **硬红线早停**：命中任一条红线即停止低权维度（网络口碑 / 抖音 / 高德），仅跑 **缩减集（参保 + 仲裁 + 套路 3 维）**后直接出报告：
   - 参保=0 / 明确不缴；
   - 主体严重混淆（简介主体 ≠ 工商主体）或 自然人独资微型壳；
   - 仲裁 / 投诉爆量（黑猫大量投诉 + 公开仲裁集中）。
5. **不做结果缓存**：每次全量重跑，换取数据新鲜度（复查 / 批量场景效率妥协）。

## 后果（Consequences）

- **正面**：典型单次时延从 2–3 分钟降到 **~40–90 秒**；命中红线时进一步降到 **~20–40 秒**；决定性场景下外部调用数显著减少。
- **成本 / 负面**：动态选维与两波式增加了 `SKILL.md` 指令复杂度；无缓存使复查 / 批量场景仍慢；工商门是早停前提，其限流兜底已用「回退全维」覆盖。
- **未变**：登录墙失败模式不受影响（属 browser-skill / 贴文本范畴，不在本 ADR 优化范围）。
- **可观测性**：建议在报告中标注「本次跑了哪些维 / 是否命中红线 / 是否回退全维」，便于审计。
